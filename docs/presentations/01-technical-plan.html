02 Executive summary

The platform is reusable. The business model is not.

What the audit found

418source files, 58,327 lines. Electron, React 19, SQLite, typed IPC, migrations and 84 test files.
38database tables describing gym memberships, leads, plans and refunds. None describes a voucher, a ledger or an allocation.
91%of renderer feature code is gym specific or must be rebuilt for accounting.

The move

Keep six platform modules. Replace five domain modules with one voucher engine. Ship creditors and debtors before stock and tax reporting.

Not in this plan

No CRM. Pipeline, follow-ups and memberships are deleted.
No cloud. No bank feeds or e-invoicing in version 1.
No payroll. Salary journals are manual until phase 9.

Why this is the cheaper path

01
The desktop stack is solved. Rebuilding it adds ten weeks and no customer value.
02
The accounting risk is in rules, not frameworks. Concentrate effort there.
03
One document table removes duplicate lifecycles for invoices, bills, notes and receipts.
The cost of being wrong: a half migrated domain leaves two truths in one database. We delete the gym tables outright and start the books on a new file.
Consequence: version 1 is an 8 week build, not an 18 week rewrite. The risk sits in accounting rules, and rules can be tested.

03 The argument

We do not have a technology problem. We have a domain problem.

S
Situation
A working Windows desktop application. Electron, React 19, SQLite through node:sqlite, typed IPC, migrations, role based access, a PDF engine and a test suite. It starts fast, installs offline and has never needed a server.
C
Complication
Its domain is a gym. Thirty-eight tables and 122 IPC channels describe leads, memberships, plans, freezes and refunds. Not one of them can post a debit and a credit. The screens look like billing, but the model underneath is subscription entitlements.
Q
Question
Do we start from zero, or rebuild the domain on a platform we already trust?
A
Answer
Rebuild the domain. Delete the gym feature modules, keep the platform, and make one voucher engine the only path that writes money to the database.

07 Target architecture

Seven layers, one write path, and rules that cannot be bypassed.

Renderer
Screens. Preview totals. Never compute a stored amount.
Preload
Typed bridge. No logic, no validation.
IPC handler
Zod at the boundary. Maps errors to stable codes.
Application
Owns the transaction. Orchestrates one use case.
Domain
Posting rules, tax, rounding, allocation. Pure functions.
Repository
Queries only. Never opens a transaction.
SQLite
WAL, foreign keys, one file, no server.

Three rules that keep it honest

The renderer never stores money. It previews with the same function, then accepts what the server returns.

A repository never opens a transaction. The use case owns the boundary, so a failure rolls back everything.

The domain never touches the database. Rules are testable without a file on disk.

What this buys

Every screen, every import and every test goes through the same posting path. There is no second way to write a ledger line, which is the usual source of a books app that stops balancing in year three.

Every screen, import and test uses the same path. There is no second way to write a ledger line.

09 The invariant

Debits equal credits is enforced in four places, not hoped for.

01
Boundary validation
Zod rejects malformed payloads before the application layer runs. Amounts must be positive integers.
02
Domain assertion
The rule produces lines, then the engine sums both sides. A mismatch throws before a single row is written.
03
Single transaction
Voucher, lines, movements, allocations and audit land together. A crash leaves nothing behind.
04
Proof, every day
Trial balance on screen, integrity report in admin, and a property test over 1,000 generated voucher sets.
// application/vouchers.ts return withTransaction(() => { const lines = rule.ledger(voucher) const dr = sum(lines.debit) const cr = sum(lines.credit) assert(dr === cr) insertVoucher(voucher) insertLedgerLines(lines) insertStockMovements(...) writeAudit(voucher, 'POST') })

What cannot happen

A voucher with 13,173.33 on one side and 13,173.34 on the other. A stock movement without its bill. A posted voucher with no audit row. A number consumed by a failed post.

A posted voucher either exists completely or it does not exist at all.

10 The paisa discipline

Tax is computed once, in integers, and rounding lands in its own account.

01Gross, quantity times rate7,700.00
02Discount, basis points, half up1,174.67
03Taxable value, nine lines13,173.33
04Place of supply decides CGST plus SGST or IGSTintra
05Tax per line, per rate group2,371.20
06Round to the rupee, difference to round off0.47
=Invoice total15,545.00

Ledger lines

Dr  Purchases     13,173.33
Dr  Input CGST   1,185.60
Dr  Input SGST   1,185.60
Dr  Round off        0.47
    Cr  Supplier    15,545.00

The printed bill says 1,185.59

Nine percent of 1,521.20 is 136.908. We round half up to 136.91, so our CGST is one paisa higher. The total is identical because round off absorbs it.

We document the difference instead of copying another system's truncation. Our books stay internally consistent.

No floats, anywhere

Money is integer paise. Quantity is integer scaled by 10,000. Percentages are basis points. One rounding function, unit tested at the half, above it and below it.

Why it matters: a one paisa error is harmless once and expensive after 40,000 invoices and one GST return.

11 Three safeguards

A posted voucher is a fact. Corrections are new facts.

Correction, not editing

DRAFT -> POSTED -> CANCELLED

Cancel writes a mirror voucher, reverses stock and allocations, and keeps both documents in the day book, linked.

The number is not reused. The original never changes.

Audited: who, when, why.

One sequence per book

SALES / INV / 2026-27
INV/0042

PURCHASE / PUR / 2026-27
PUR/0118

The number is allocated inside the posting transaction. A rollback does not consume it.

Cancelled vouchers keep their number, so the audit trail has no holes.

A double click posts once

Every mutation carries a request key. The second call returns the first result instead of writing a second voucher.

POST /vouchers
key: 7f3a-...
200 voucher INV/0042
repeat, same key
200 voucher INV/0042

Same key, different payload: conflict, refused.

Property test

Generate 1,000 voucher sets. Post all of them. Assert that every voucher balances, the trial balance equals the raw ledger sums, and cancelling a random subset returns the books to the prior state.

Blocking conditions

A new `any` in the main process. An edited migration. A new IPC channel without a contract. Coverage under the floor.
